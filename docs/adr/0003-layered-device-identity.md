# ADR 0003：分层设备身份，概率关联封顶 0.6

**状态**：已采纳
**日期**：2026-07-31

## 背景

需求："生成设备唯一 ID 绑定用户，**用户切换浏览器也需要能识别**"，且无账号体系。

调研结论是这个需求**只能部分满足**：

- 高熵指纹信号（canvas、音频、字体）**是浏览器相关的**——不同引擎的光栅化与抗锯齿必然不同。它们识别浏览器，不识别设备。
- 跨浏览器稳定的信号（时区、OS、CPU 核数、内存、屏幕）合计仅约 **10-15 bits 且高度相关**。
- FingerprintJS 维护者明确表态：同设备不同浏览器得到不同 ID 是"正确且符合预期的行为"；其商业版 99.5% 准确率是**按浏览器**计。
- 学术界最佳（Cao et al., NDSS 2017）跨浏览器唯一性 83.24%——**约 17% 用户会与陌生人碰撞**——且该数据早于 Safari 26 默认开启的指纹防护。

## 决策

**分层方案**：

1. **确定性层（~99%）**：服务端 UUIDv7，经 HttpOnly Cookie + 响应体（供客户端镜像到 localStorage）双通道下发。这是业务真正绑定的 `device_id`。
2. **概率层（置信度封顶 0.6）**：浏览器无关信号 + IP 段的哈希，把新浏览器关联到已有 `visitor`。**仅作提示，永不作为身份。**

三条硬性护栏：

- **置信度上限 0.6**，由 `LinkConfidence.Create` 强制钳位，调用方无法把猜测抬升成事实。
- **`MaxCoarseFanout = 5`**：共享同一粗指纹的设备超过 5 台时**拒绝关联**。
- **关联是可逆的边**（`device_link`），永不做破坏性行合并；置信度只升不降。

## 理由

`MaxCoarseFanout` 是整个设计中最关键的一条。在 10-15 bits 熵的前提下，**一个共用 NAT 出口的办公室会让几十台陌生设备落到同一个 `(fp_coarse, ip_prefix)`**。没有基数上限，系统会把他们全部焊成一个巨型 visitor——把一个人的行为记到另一个人头上。

原则：**低熵指纹只有在同时"罕见"时才允许关联。**

歧义一律解析为新建 visitor。**错误合并比重复账号昂贵得多**：前者静默地张冠李戴，后者只是多一行数据。

## 实测

对原生 AOT 二进制的验证：跨浏览器场景（stable 相同、volatile 不同、无 Cookie）确实产生新 `device_id` 但关联到同一 `visitor_id`，置信度 0.6；第 6 台共享指纹的设备起，系统**拒绝关联**并新建 visitor。

正反两个方向都验证过——只会关联、从不拒绝的实现等于没有实现这个护栏。

## 代价

- 跨浏览器识别是尽力而为，不是保证。业务规则必须按置信度分级：只有 1.0 才能用于硬性放行/拦截，0.6 最多用于增加摩擦。
- 需要合规工作：EDPB Guidelines 2/2023 认定指纹采集适用 ePrivacy 第 5(3) 条，**需事先同意**，"无 Cookie"不等于免同意；中国 PIPL 将设备指纹视为个人信息。

## 如果需要硬保证

浏览器沙箱内做不到。可靠路径只有：原生 App、账号登录、手机/邮箱验证、设备绑定 passkey。
